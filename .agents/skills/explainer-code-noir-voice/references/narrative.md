# Reasoning through code and its consequences

The primary anchor is a question or a small piece of code/data. The story need not maintain a physical object or follow six tutorial phases. Design the reading path and explanation together.

A common useful arc: show a surprising result → establish the minimum code that produces it → expose the decisive distinction → show the changed result → state a bounded rule. This is an option, not a mandate. For a concept without a surprising result, start with a practical choice or a prediction. Never invent a novice misconception simply to knock it down.

## What each beat earns

Record the question being resolved, the exact screen evidence, the spoken causal link and what the viewer should now understand. Name the visual anchor and its before/change/after states alongside that clause. Evidence may be a native spatial model, recognizable asset or labelled illustration as well as code. Choose this while scripting, not as decoration after locking the paragraphs. The decisive line can be the main subject of a scene. An output can occupy the whole reading area when it resolves a prediction. A short comparison can stay still while narration explains why its two sides differ.

Use the source's brevity and emphatic pauses inside connected prose. Avoid a string of slogans, mysterious terms or code jokes with no explanation. A giant “POWER;” works rhetorically in the reference but teaches no programming mechanism on its own.

For novices: introduce syntax as it becomes necessary; give ordinary-language labels to output and stored values. Do not call everything a terminal. For experienced viewers: shorten setup and focus on the less obvious boundary or tradeoff. Scope remains one concept.

## Evidence comes before conclusion

When explaining execution, show the relevant input/code before its result. Keep labels explicit: “printed output” is different from “value of x” or “return value.” Do not infer a value from the program's visible text. Verify snippets in their stated language/version where semantics matter. Make comparisons controlled: change the relevant line, keep the input and function name stable, and state what the change did.

A function can both print and return; the contrast must not imply mutual exclusion. A no-return rule in the model script is about ordinary Python functions, not all languages or generators/coroutines. Pick only the caveats necessary for the actual audience; precision does not require a survey of every exception.

The sample uses one concrete computation, 2 + 3, to distinguish two destinations. The example is evidence for the stated distinction, not evidence that all side effects or all function semantics are now covered.

## Voice and emphasis

Write the voice as prose, not as literal punctuation narration. Read an unfamiliar symbol when its meaning matters. Screen copy compresses what must be remembered, while the voice supplies why/how. Code should not be paraphrased into invalid syntax for aesthetics.

Prefer whole-line or meaningful-phrase reveals and a restrained cue on the decisive keyword. No character-by-character typing by default, blinking cursor loops, fake compilation, simulated errors for decoration or continuous zoom. Let the result settle during explanation. A quiet interval is for a question such as “What will x receive?”; specify that task, then answer it.

A final rule should transfer beyond the example and answer the opening question. End with that rule or a relevant self-check, not a forced comment/follow prompt.

## When typography needs a visual partner

A term such as “current directory” benefits from an identifiable location marker. A path benefits from an actual branch, a return value from a destination, a process from a visible boundary. Establish that visual early, then reuse and change it so the viewer can follow the explanation across cuts. Remove redundant prose to make room; do not simply append an icon below every block. The story can move from question typography to concrete model to evidence to a short rule.

The terminal trial showed that correct syntax and readable text can still produce a monotonous video. Most scenes reused one title with static lines underneath. The reusable correction is to design a changing relationship with an explanatory visual anchor; it is not to require file trees in unrelated topics or continuous animation during reading.
