# Build one technical board over time

Plan states rather than slides: what modules exist, what is known, what operation happens, what changes, and what stays
fixed. Maintain object identity across scenes. The viewer should be able to follow the worked example by watching the
board even with captions muted.

| Explanatory job | Native motion |
| --- | --- |
| Introduce an object | `show` a module and its status label. |
| Reveal stored content | `open` a native container or expose a native field. |
| Establish a relationship | `focus`, then `connect` in the actual direction. |
| Copy or pass information | `transfer` a labeled token from source to destination. |
| Mutate a value | `write`, then leave the committed result visible. |
| Bridge analogy to notation | `morph` the native module while preserving identity. |
| Reorganize the model | `move` the same module; redraw stale connections. |
| Tie code to outcome | `code` plus the operation caused by that instruction. |

Use off-white lines for established structure and red for only the current diagnostic or state transition. A transfer
does not erase the source unless an explicit operation does so. A displayed address is symbolic unless sourced as a
real runtime value. Physical travel is an explanation of dependency, not a claim about hardware timing.

Anchor actions to phrases actually spoken in `vo`. Leave enough time for a token to arrive before the next dependent
change. Keep simultaneous activity low until the relationship is familiar. Generated images may fade or move as
secondary composition, but they never act as data sources, storage, targets or program state.
